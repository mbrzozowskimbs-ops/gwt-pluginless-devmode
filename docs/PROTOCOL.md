# Pluginless DevMode bridge protocol

The protocol between `devmode-bridge.js` (browser) and `BridgeServer` (JVM). The bridge translates it 1:1 into the native `BrowserChannel` v3 protocol it speaks with the GWT DevMode code server (port `-codeServerPort`, 9997 by default).

## Transport

| Item | Value |
|---|---|
| Request | `POST http://<gwt.codesvr>/pluginless-devmode/session/<sessionId>` |
| `sessionId` | random UUID generated by the page in `connect()` |
| Request body | JSON: an array of browser **messages** |
| Response body | JSON: an array of **commands** for the browser |
| Content-Type | `text/plain;charset=UTF-8` (a CORS "simple" request, no preflight) |
| Mode | synchronous XHR — the page's JS thread waits for the response |
| Page close | `navigator.sendBeacon` with `[["quit"]]` (synchronous XHR is not allowed during unload) |
| Health check | `GET /pluginless-devmode/health` → `ok` |

The bridge accepts requests only with a `Host` header that points to loopback (protection against DNS rebinding) and an allowed `Origin` (by default any `localhost` / `127.0.0.1` / `[::1]` origin, narrowed with `--allow-origin`). The response sets `Access-Control-Allow-Origin` to the request's `Origin`.

Session errors (lost connection to DevMode, protocol error, unknown session) are returned as HTTP 200 with an `error` command, so the page can display them. Status codes 403/404/405 are used only for requests that never reach a session.

## Values

| JSON | Meaning | `BrowserChannel.Value` |
|---|---|---|
| `null` | `null` | NULL |
| `true` / `false` | boolean | BOOLEAN |
| integer within the `int` range | number | INT (browser → JVM) |
| any other number | number | DOUBLE |
| `"text"` | string | STRING |
| `["u"]` | `undefined` | UNDEFINED |
| `["d", "NaN" \| "Infinity" \| "-Infinity"]` | non-finite number | DOUBLE |
| `["j", id]` | Java object (code server reference) | JAVA_OBJECT |
| `["o", id]` | JS object (browser reference) | JS_OBJECT |

In the JVM → browser direction, INT, SHORT, BYTE and CHAR arrive as numbers.

## Browser messages

All messages in a batch except the last one must be asynchronous (in practice: `stats` and `free`). The response refers to the last message.

| Message | BrowserChannel | Response |
|---|---|---|
| `["connect", hostedHtmlVersion, url, tabKey, sessionKey, moduleName, userAgent]` | `CHECK_VERSIONS` (3..3) → `PROTOCOL_VERSION`, then `LOAD_MODULE` | commands up to the `return` with the result of `onModuleLoad` |
| `["invoke", dispId, thisValue, [args]]` | `INVOKE` (JS → Java) | commands up to `return` |
| `["getJava", javaObjectId, dispId]` | `INVOKE_SPECIAL GetProperty` | commands up to `return` |
| `["setJava", javaObjectId, dispId, value]` | `INVOKE_SPECIAL SetProperty` | commands up to `return` |
| `["return", isException, value]` | `RETURN` (result of a JVM request) | commands up to the next JVM request or `return` |
| `["free", [javaObjectIds]]` | `FREE_VALUE` | none (asynchronous) |
| `["stats", [page, bridge, xhr, js, jsni]]` | — (bridge only) | none (asynchronous); cumulative browser phase times in µs since page load, sent at the start of every batch, used for round trip statistics (`BridgeStats`) |
| `["quit"]` | `QUIT`, closes the session | `[]` |

## Bridge commands

A response is zero or more asynchronous commands followed by exactly one final command.

| Command | Kind | Browser action |
|---|---|---|
| `["jsni", code]` | asynchronous | `window.eval(code)` in the global scope of the module window |
| `["free", [jsObjectIds]]` | asynchronous | forget the JS objects with these ids |
| `["invoke", methodName, thisValue, [args]]` | final (request) | `__gwt_jsInvoke(this, methodName, ...args)`, reply with `return` |
| `["get", jsObjectId, key]` | final (request) | read a property, reply with `return` |
| `["set", jsObjectId, key, value]` | final (request) | write a property, reply with `return` |
| `["return", isException, value]` | final | result of the message sent by the browser |
| `["quit"]` | final | the code server closed the session |
| `["error", message]` | final | bridge error; the session is closed |

The bridge handles `REQUEST_ICON` from the code server itself (it answers `USER_AGENT_ICON` with no icon). It rejects any `INVOKE_SPECIAL` other than Get/SetProperty with an exception, as the original plugins did.

## Trampoline loop (browser)

```
transact(message):
  repeat:
    commands = POST(message)
    run asynchronous commands (jsni, free)
    final = last command
    if return          → return its result
    if invoke/get/set  → run it, message = ["return", ...]; continue the loop
    if quit/error      → show a message, throw
```

Sequential Java → JS calls made by one Java method are handled inside this loop, so they do not grow the JS stack: 100,000 calls in a row run at constant stack depth. The stack grows only with real nesting, when JS code called from Java calls Java again and so re-enters `transact()`.

## Java objects in the browser

A Java object is a `Proxy` over a bound function (callable, without a non-configurable `prototype`), following the `JavaObject` semantics of the NPAPI plugin:

| JS operation | Effect |
|---|---|
| `obj[n]` (n is a number) | `getJava(id, n)` — reads a field by dispId |
| `obj[n] = v` | `setJava(id, n, v)` |
| `obj.toString` | tear-off `__gwt_makeTearOff(null, 0, 0)` — dispId 0 is `toString()` |
| `obj.__gwt_ObjectId` | the object id |
| `obj(dispId, thisObj, ...args)` | `invoke(dispId, thisObj or obj, args)`; the result is wrapped by `__gwt_makeResult` |
| `Symbol` keys and other names | `undefined` (no Java counterpart) |

Wrappers are held through `WeakRef`. Once the garbage collector reclaims them (`FinalizationRegistry`), their ids are sent in a `free` message prepended to the next request.
